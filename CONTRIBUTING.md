# Участие в разработке

Начните с [установки](docs/INSTALL.md), [тестов](docs/TESTING.md) и
[границ исследовательских утверждений](docs/RESEARCH_STATUS.md).
Актуальный пакет и его тесты находятся в `src/lm_suti_assurance/` и `tests/`;
сохранённый HTTP/OAuth/ledger/DAV runtime и его тесты — в `live_math_mcp_prod/`.
Production-композиция находится в `tools/release_v01_entry.py`.
Перед изменением MCP прочитайте [архитектуру](ARCHITECTURE.md) и
[контракт интерфейса](docs/MCP_INTERFACE.md).

Используйте четыре пробела, `snake_case` для функций, `PascalCase` для классов,
верхний регистр для констант и type hints на публичных интерфейсах.
Сохраняйте существующие модульные границы, избегайте общего переформатирования.
Ruff/mypy используются для затронутых новых модулей; старый код не заявляется
полностью приведённым к единому строгому стилю.

Для изменений SQLite нужны временная база, проверка миграции, idempotency,
project isolation, append-only истории и hash-chain. Для MCP-схем дополнительно
нужен реальный клиент с tools/list и вызовом инструмента. Не используйте живую
базу для тестов и не меняйте исторические результаты ради нового PASS.

Коммит: короткий повелительный subject, например `Fix scoped completion evidence`.
PR должен описывать проблему и новое поведение, команды и результаты проверок,
изменения схем/протокола и необходимость миграции. Ссылку на issue добавляйте,
если он есть. Скриншоты нужны только при изменении интерфейса.

Новые предложения автору SUTI оформляйте в
`suti_author_proposals/NNN-short-topic/README.md` по существующему шаблону.
Разделяйте предложение, локальную проверку и действительный ответ автора.
Публикация карточки не означает согласования её смысла.

Не добавляйте базы, backup, OAuth credentials, `.env`, model spool или сырые
клиентские журналы. Источниковые примеры должны иметь действительное происхождение;
модельные выводы не получают математический `verified` автоматически.

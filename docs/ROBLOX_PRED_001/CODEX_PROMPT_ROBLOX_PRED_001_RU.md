# Промпт для Codex — ROBLOX-PRED-001

Ты — автономный исследовательский кодовый агент. Твоя задача — реализовать первую исполняемую версию коммерчески ориентированного сравнительного исследования Roblox-проектов по приложенному `TZ_ROBLOX_PRED_001_RU.md`.

**Главное:** это adversarial benchmark смыслово-структурной системы SOMA/DAVE/SUTI/LevinMass против сильного обычного ML и гибрида. Не пытайся обеспечить победу новой теории. Отрицательный результат с качественным RCA лучше ложноположительного.

## Первое действие

1. Прочитай ТЗ целиком и исследуй текущий репозиторий. Не ломай существующие проекты, не меняй файлы за пределами своей директории без причины.
2. Найди локальные описания/конфиги/подключения SOMA, DAVE, SUTI, LivingMath/MCP. Если доступ к MCP есть, выполни безопасный capability discovery. Если нет — создай корректный adapter contract и `UNAVAILABLE` status; **не выдумывай endpoint, методы, ответ сервера и выполненные расчёты.**
3. Сначала Stage 0: легальный и технический аудит источников Roblox; проверь хотя бы небольшое количество реальных запросов по актуальным документированным контрактам, если сеть разрешена. Фиксируй статус, метаданные времени, лицензию и результаты в `docs/DATA_AUDIT_RU.md`.
4. Реши, доступен ли ретроспективный benchmark, перспективный сбор, оба или ни один, исходя из доказанных фактов.
5. Только после этого — минимальный Stage 1 baseline, который можно быстро запустить и тестировать. Не переходи к дорогостоящим этапам, если dataset невалиден.

## Жёсткие технические инварианты

- `known_at <= t0` для каждого feature, включая *версию* названия, описания, картинок и историю создателя. Текущие описания исторических игр нельзя притворять старым текстом.
- Цель по стабильной будущей аудитории, revenue только с подтверждёнными источниками.
- Unknown != zero. Missingness честно кодировать.
- Датасет не формируется из одних победителей; selection bias и censored games отражать в отчёте.
- Валидация time-forward, train/validation/test, group creator/clone discipline и horizon embargo.
- Система SUTI не является названием для самописного parser. Любой простейший heuristic extractor — явно отдельный контроль, не `S1 native`.
- Никаких неправомерных scrape/обходов rate limits/auth и неизвестных условий лицензирования.
- Не применять случайный `train_test_split` как главный результат. Не оптимизировать test, не показывать тестовые результаты до заморозки протокола.
- Не выдавать синтетические smoke fixtures за реальную оценку качества.
- Снизить сложность, а не вводить новые DSL, распределённые очереди, Kubernetes, тяжелые БД, фронтенд или LLM-тренировку без необходимости.
- Все выводы и отчёты — на русском; код, типы, API и имена полей — на английском.

## Реализация — порядок

**Итерация A (обязательная сейчас):**
- создать структуру репозитория и `pyproject.toml`;
- реализовать data audit/registry и небольшой легальный коннектор для реально подтверждённого источника, либо stub с ясным `unavailable`;
- определить typed tables/schemas и parquet/duckdb ingest;
- валидатор as-of с жёсткими тестами на future leakage;
- реализовать train-time threshold, temporal split и M0/M1 с CatBoost или sklearn fallback;
- написать `README_RU.md` с командами запуска;
- прогнать pytest и короткий smoke run;
- выдать `STAGE0_STAGE1_REPORT_RU.md`, где ясно отделены реальные данные, синтетические fixtures и пока недоступные результаты.

**Итерация B (после успешного data gate):**
- реализовать M2 с TF-IDF / embeddings;
- сделать SUTI capability audit и adapter, dry-run fixture;
- если доступны реальные методы — подключить их без подмены;
- определить экспорт structural features и матрицу абляций;
- добавить H1 и негативные контроли.

**Итерация C (только при наличии допустимых данных):**
- строгое time-forward сравнение, CI/калибровка, жанровые и creator-holdouts, RCA, экономические сценарии.

## Definition of Done для первого запуска

В конце первой итерации должна быть работоспособная кодовая база с тестами и честным ответом на три вопроса:

1. **Есть ли доказуемо доступные исторические данные до момента прогноза и будущие outcomes?** Приведи конкретные источники, границы, лицензии, количество проверенных игр и диапазон дат.
2. **Можем ли мы провести валидный ML baseline сейчас?** Если да — реальные метрики и размер независимой выборки с указанием смещений. Если нет — `INCONCLUSIVE` и конкретный минимальный способ получить данные.
3. **Какие реальные вычислительные операции SOMA/DAVE/SUTI доступны?** Приложи список обнаруженных инструментов, входов/выходов, ограничения; недоступность отдельно.

В итоговом ответе укажи: commit hash (если git), структуру созданных файлов, прошедшие/упавшие тесты, выполненные команды, data gate, реальные измерения, препятствия, одно наиболее полезное следующее действие. Не заявляй успех там, где теста не было.

**Начинай работу сразу; не проси подтверждения рутинных решений. Если доступ к внешнему источнику отсутствует, не застревай: зафиксируй блокер, оставь проверяемый код и переходи к следующей независимой части.**

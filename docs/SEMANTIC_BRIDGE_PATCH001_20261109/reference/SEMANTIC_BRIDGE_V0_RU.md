# Semantic Bridge v0 — теория контекстно-различающей формализации

**Статус:** проектная спецификация, 09.11.2026. Не реализованная возможность действующего MCP.  
**Контекст:** LivingMath / UDAV / White Star / Formal Bridge / NOBS / SEq.  
**Задача:** связать LLM-генерацию интерпретаций с верифицируемым исследованием их структурных отношений, не передавая серверу ответственность за понимание естественного текста.

## 0. Статус исходных утверждений

**Наблюдалось в прежнем эксперименте:** источник `UDAV_AB_MATH_20261109/REPORT_RU.md`: контроль `source_only` и `white_star_structural` по четырём русским текстам имел 4/4 адекватных первичных реакций в обеих ветках; прироста точности не установлено. В обоих вариантах модель предложила корректные первичные формулы для Q1–Q3 и отказалась от необоснованной формализации Q4. Замороженный `NO_MOVE/REAL_TRACE/SHAM_ORDER/PRIMITIVE_CLOSURE` не выявил прироста выразительной силы от REAL_TRACE в ограниченном классе. Интеграция `udav_core` в `formal_nl_propose` отсутствует; принимаются `symbolic_v1` и `white_star`.

**Проверено по исходникам GitHub `catman77/LivingMath` (ветка main):**

- `src/lm_suti_assurance/nl_proposal/provenance.py` извлекает проверенный порядок текстовых spans из символьной истории. При отсутствии заданных `node_refs` по умолчанию выбирает узлы `REVERSE`.
- `src/lm_suti_assurance/nl_proposal/decoder.py`: `build_move` переставляет *внешний spine кванторов* по позициям source-linked binders; `typecheck` проверяет формальную типизацию нового AST. `source_licensed=False` — корректная оговорка реализации, но геометрии смысла это не создаёт.
- `src/lm_suti_assurance/nl_proposal/provider.py`: LLM вызывается внутри `formal_nl_propose` как отдельный owner-hosted провайдер. Это не тот архитектурный режим, в котором *клиентская* LLM создаёт все математические гипотезы, а MCP только исследует структуры.
- `src/lm_suti_assurance/udav_core/frontier.py` — фронтир по `(node, operator, parameter)`, сырая / quotient-новизна и provenance. Поиск не имеет объекта «предполагаемый смысл текста».
- `src/lm_suti_assurance/formal_bridge/fol.py` реализует типизированные конечные FOL-модели и их проверку, но ограниченный словарь FOL не выражает весь NL, в частности модальные/прагматические утверждения.

Дальнейшие определения — **предложение**, не сообщение о существующих возможностях сервера.

## 1. Основное разделение труда

**LLM** выбирает постановку, сигнатуру, возможные смыслы текста, контекст, формальные гипотезы, релевантность проверочных сценариев, решает, что в итоге передать как формализацию. **MCP** сохраняет и преобразует типизированные кандидаты, рассчитывает инварианты, строит формальные отношения, проверяет доказательства, находит конечные контрмодели, хранит provenance и сообщает о незакрытых обязательствах.

Ни один `MCP_PASS` не равен утверждению «формула верно выражает авторский смысл». Это отдельное семантическое обязательство, которое может быть разрешено внешним оценщиком, пользователем или определённым для конкретной задачи наблюдательным протоколом. Сервер не придумывает метки смысла.

Данные, целиком вычисленные из текста, не создают независимой информации об авторском намерении. Но они могут снижать *вычислительную* сложность исследования интерпретаций. Это и есть наш механизм пользы.

## 2. Формальная постановка

Пусть:

- `x ∈ Text` — UTF-8 источник со стабильным SHA-256 и spans;
- `c ∈ Context` — доступный контекст (может быть частичным);
- `τ` — задача (formalize / compare / invent / transfer);
- `Σ` — предложенная LLM типизированная сигнатура с provenance и явными ограничениями;
- `Form(Σ)` — множество корректно типизированных выражений языка данной версии;
- `J(x,c)` — неизвестное (вообще говоря, многозначное) отношение интерпретации текста; **не реализовано и не постулировано как доступный oracle**.

LLM создаёт *кандидат*, а не установленное значение:

\[
 h_i=(\varphi_i,\;\gamma_i,\;A_i,\;U_i,\;\Sigma_i),\qquad \varphi_i\in Form(\Sigma_i).
\]

Здесь `γ_i` — graph привязок узлов AST и ролей переменных к spans/контекстам; `A_i` — открыто добавленные предпосылки; `U_i` — зафиксированные неоднозначности, неподдержанные фрагменты и ожидающие проверки обязательства. `γ_i` удостоверяет **происхождение утверждения**, но не его смысловую истинность.

Далее сервер вычисляет

\[
 \mathcal B(H,Q)=\bigl(H,\mathcal R_{\Sigma}(H),\mathcal C(H),\mathcal O_Q(H),\mathcal W(H)\bigr),
\]

где `H={h_1,…,h_k}`;

- `\mathcal R_Σ` — типизированные отношения между AST;
- `\mathcal C` — proof terms / явные конечные countermodels / scope-оговорки;
- `\mathcal O_Q` — наблюдаемые различия при заданных сценариях `Q`;
- `\mathcal W` — открытые obligations и provenance.

Именно LLM анализирует `\mathcal B` и предлагает следующий `H'`, уточняющий вопрос либо финальную формализацию.

### 2.1. Неотождествление кандидатов

Унификация синтаксиса, равенство нормальных форм, эквивалентность в ограниченном семействе конечных моделей и соответствие смыслу исходного текста — четыре разных отношения.

Финитный результат `SAME_ON_BOUND` означает только отсутствие найденного контрпримера в **явно указанном** семействе моделей. Он не даёт права выполнять quotient как при доказанной эквивалентности. Разные source spans, histories, assumptions сохраняются и в случае одинакового AST.

## 3. Основные структуры

### 3.1. ContextualHypothesis

```text
ContextualHypothesis = {
  id, source_ref, context_ref?, task_ref,
  signature, formula_ast, typed_spans,
  assumptions[], unsupported[], uncertainty[],
  origin: LLM_PROPOSED,
  typecheck_receipt?, proof_obligations[]
}
```

Объект с именем `SemanticStructure` **не означает**, что её семантика доказана. Это гипотеза о смысле; допустимое преобразование обязано явно указывать отношение к исходной формуле.

### 3.2. StructuralRelation

```text
StructuralRelation = {
  source_hypothesis_id, target_hypothesis_id,
  relation_kind, scope, certificate?,
  type_status, source_alignment_status,
  unresolved_obligations[], provenance
}
```

В первой версии допустимы статусы:

- `ALPHA_EQ`: проверено переименование связанных переменных без захвата;
- `PROVED_EQ`: независимый верификатор принял логическое доказательство эквивалентности в заявленной системе;
- `PROVED_ENTAILMENT`: проверено `φ ⇒ ψ` (с чётким направлением);
- `COUNTERMODEL_SEPARATES`: явная модель `M` и значения `M⊨φ`, `M⊭ψ` или наоборот (этого достаточно для опровержения универсальной эквивалентности);
- `SAME_ON_BOUND`: конечные тесты не различили, **не доказанная эквивалентность**;
- `UNKNOWN`: не установлено ни отношение, ни разделяющая модель в бюджете.

Не смешивать `PROVED_ENTAILMENT` и `STRONGER_ON_BOUND`: последняя — только конечное наблюдение. `SOURCE_LICENSED` не может выставляться этими операциями автоматически.

### 3.3. Task-specific observer

Внешняя LLM предлагает набор проверочных сценариев `Q={q_1,...,q_m}`. MCP компилирует корректно типизированные сценарии в конкретные модели `M_i` и вычисляет

\[
 O_Q(\varphi)=(v_{M_1}(\varphi),\ldots,v_{M_m}(\varphi)),
 \quad v_M\in\{\mathrm{TRUE},\mathrm{FALSE},\mathrm{UNKNOWN}\}.
\]

`UNKNOWN` нужен, если модель не замкнута, выражение неподдержано либо вычисление не доведено до решения. Для закрытых конечных моделей это обычный model check. Выбор `Q` — часть исследовательской программы LLM, а не универсальная лингвистическая эвристика.

Сервер может **сам** построить минимальную конечную модель, разделяющую две формулы, перебором/solver'ом. Это вычисление в заданной сигнатуре, а не извлечение авторского намерения.

### 3.4. Proof obligations

Отдельно хранить:

`AST_WELL_TYPED`; `SIGNATURE_SUPPORTED`; `SOURCE_SPANS_VALID`; `ASSUMPTIONS_EXPLICIT`; `FORMAL_RELATION_CERTIFIED`; `CONTEXT_SCENARIO_LICENSED`; `SOURCE_MEANING_ADJUDICATED`; `GENERALIZATION_SCOPE_CHECKED`.

Ни одно из них нельзя автоматически считать выполненным вследствие другого.

## 4. Законы слоя

**SB1. Внешнее происхождение гипотез.** В режиме `SemanticBridge v0` MCP не вызывает модель, не создаёт текстовую интерпретацию и не присваивает содержательную значимость. Он выполняет арифметику над переданными кандидатами и выдаёт проверочные объекты.

**SB2. Soundness formal certificates.** Для `PROVED_EQ`, `PROVED_ENTAILMENT` требуется принятие доказательства выделенным проверяющим ядром. Для `COUNTERMODEL_SEPARATES` достаточно конечной структуры с проверенными истинностными значениями обоих выражений. Ограниченный перебор без контрмодели — не доказательство.

**SB3. Conservative source grounding.** Ни формальные преобразования, ни переобозначения в сырой строке не порождают новых заявлений о содержании исходного текста. Любое преобразование с новым предположением порождает новое явное обязательство.

**SB4. No premature quotient.** Не разрешается стирать provenance / assumptions / history на основании одинакового выходного AST, конечного совпадения значений или похожести символных signatures. Quotient возможен только для явно указанного отношения эквивалентности.

**SB5. Различение поиска и сохранения.** Некорректный как перевод исходного текста, но корректный как математический объект кандидат может оставаться в графе гипотез с меткой `ALTERNATIVE_NOT_SOURCE_LICENSED`. Он потенциально полезен для творческих переносов и контрпримеров.

**SB6. Task-dependent expressivity.** Если сигнатура/язык не представляют часть смысла, возвращается `LANGUAGE_INSUFFICIENT`, с фрагментом источника и объяснением недостающей возможности. Увеличение логического языка предлагается LLM и выполняется только после явного согласования сигнатуры.

**SB7. Контролируемая неединственность.** Несколько гипотез могут быть совместимы с доступными контекстами. Сервер не обязан выдавать одну «истинную». Для каждой пары различимых гипотез разрешён запрос различающего сценария.

**SB8. Replay/идентичность.** Все AST, источники, models, инварианты и проверки имеют хеши, отдельные статусы proof vs exploratory, явные версии checker'а и воспроизводимую процедуру.

## 5. No-go: почему старый путь не мог работать как универсальный мост

Пусть `F(x)` — вычисляемое лишь из текста наблюдение `SPLIT/REVERSE/RENAME/alpha-pattern`. Предположим, что для одного и того же наблюдения существуют два допустимых контекста с несовместимыми интерпретациями. Тогда не существует функции `G(F(x))`, которая без передачи контекста правильно восстановит обе интерпретации: для одинакового аргумента `G` должна была бы вернуть два разных единственных значения.

Это **условная теорема о недостаточности наблюдателя**, а не опровержение вычислительной пользы `F`. Вычислительная польза появляется, когда `F` строит сложные, но верифицируемые следствия конкретных гипотез, позволяя LLM совершать более качественный поиск.

## 6. Минимальный математический пример

В сигнатуре `Researcher, Hypothesis; Checked(r,h)` модель предлагает две формулы:

\[
 \varphi=\forall r\,\exists h\; Checked(r,h),\qquad
 \psi=\exists h\,\forall r\; Checked(r,h).
\]

**Отношение:** `ψ ⇒ φ` действительно для всех структур (обычная семантика с непустыми сортами; в частности в установленной реализации сорта непусты). Обратное неверно.

**Явная контрмодель:** исследователи `r0,r1`, гипотезы `h0,h1`, отношение `Checked={(r0,h0),(r1,h1)}`. `φ=TRUE`, `ψ=FALSE`.

Модель не устанавливает, что именно `φ` — верное прочтение русского предложения: это решает LLM по исходному тексту/контексту. Но сервер выдаёт точное различение, которое помогает LLM увидеть смысл перестановки кванторов.

## 7. Сложный контрольный пример (без «золотого» ответа в сервере)

Текст:

> Каждый исследователь сообщил своему руководителю обо всех гипотезах, которые он проверил, но не сообщил о тех, которые только предполагал проверить.

LLM может предложить сигнатуру с `Researcher`, `Manager`, `Hypothesis`, `Supervises(m,r)`, `Checked(r,h)`, `Planned(r,h)`, `Reported(r,m,h)`. Кандидат (с явно внесённой интерпретацией «только предполагал» как `Planned ∧ ¬Checked`):

\[
\forall r\,\forall m\big(Supervises(m,r)\Rightarrow
 [\forall h(Checked(r,h)\Rightarrow Reported(r,m,h))\ \land\
 \forall h((Planned(r,h)\land\neg Checked(r,h))\Rightarrow\neg Reported(r,m,h))]\big).
\]

**Необходимые оговорки:** выражение не утверждает существования руководителя и не закрепляет его единственность; если это содержательно требуется, добавить соответствующие аксиомы либо функцию supervisor. Времена событий и значение «только предполагал» также нуждаются в контексте. Сервер не вправе замалчивать эти обязательства.

Варианты интерпретаций могут отличаться областью действия отрицания, отношением `Checked/Planned`, референтом местоимения «он», существованием руководителя. MCP должен вернуть моделируемые контрасты по каждому вопросу; LLM решает, какие из них соответствуют тексту.

## 8. Интерфейс v0 (концептуальный, не существующие MCP-методы)

```
bridge_register_hypotheses(source_ref, context_ref?, task, hypotheses[])
  -> immutable hypothesis_refs, typecheck, source spans, obligations

bridge_contrast(hypothesis_refs[], relation_budget)
  -> formal_relations, proof/countermodel witnesses, UNKNOWN

bridge_find_distinguishing_model(phi_ref, psi_ref, bounds)
  -> finite_model+truth_values | BOUNDED_NO_SEPARATOR | UNSUPPORTED

bridge_eval_scenarios(hypothesis_refs[], scenario_refs[])
  -> typed observation vectors, proof scope, UNKNOWN

bridge_replay(bundle_ref)
  -> exact bound/hash verification or explicit error
```

В текущей реализации уже есть части конвейера: сохранение formal source, FOL typecheck, конечные модели, проверка происхождения, `udav` provenance и replay. Новые методы следует делать **тонкой композиционной надстройкой**, не переносить into-MCP LLM generation и не модифицировать native алгоритм Белой звезды. Отдельный `udav_symbolic_explore` adapter подключать только как source-bound *data-only* поставщик, без автоматической смысловой лицензии.

## 9. Критерий готовности перед написанием ТЗ кодовому агенту

### Теоретические обязательства

1. Определено, какое отношение является теоретической эквивалентностью, а какое — лишь конечной неразличимостью.
2. Все переходы между `Text`, `AST`, `Model`, `SourceMeaning` имеют отдельный provenance/status.
3. Есть хотя бы один предъявляемый контрпример к неправомерному преобразованию и один корректный `ALPHA_EQ`-пример.
4. Установлена граница поддерживаемого языка и способ возвращать `LANGUAGE_INSUFFICIENT` вместо фантазии.
5. Подтверждено, что MCP не требует определённого размера или конкретного производителя LLM.

### Малый различающий эксперимент

Для одного заранее замороженного сложного текста LLM выдаёт гипотезы `H` *до* чтения контрмоделей. Сервер исследует четыре пары:

- действительно эквивалентную с точностью до alpha;
- истинное усиление/ослабление;
- несравнимые интерпретации;
- неподдержанное выражение (отчёт об ограничении языка).

Второй проход LLM должен исправить **конкретную ошибку**, с опорой на свидетельство и без потери корректных частей. Контроль: без контрмодели и с переставленными provenance (sham). Верный успех — проверенное улучшение на независимой семантической оценке; простое увеличение числа AST не является успехом. Если и без контрмодели исправлено то же самое, причинная добавка MCP не продемонстрирована.

### Формальное правило перехода

Никакое `TYPECHECK=PASS`, `REPLAY_MATCH`, `FINITE_SAME` или `SOURCE_SHA_MATCH` не допускается отображать в `SEMANTICALLY_VERIFIED`. Именно это сохраняет разделение труда.

## 10. Риски и нерешённые задачи

- **Выразительность:** FOL не выражает произвольную модальность/темпоральность; не расширять его молча.
- **Контекст:** отсутствующие факты не могут возникать из детерминированной перестановки символов.
- **Зависимость от LLM:** предложенные текстовые привязки могут быть неверными; источник связывает байты, не значение.
- **Слишком маленькие модели:** finite bound не подтверждает общую эквивалентность; минимальные контрмодели всё же дают валидное опровержение.
- **Потеря структуры:** преждевременное объединение AST/историй по одному хешу наблюдения скрывает полезные различия.
- **Ложная эффективность:** при слишком простом корпусе `LLM-only` уже на потолке; выбрать трудный, независимо размеченный текст и фиксировать errors corrected, не «генераций на секунду».

## 11. Следующий переход

Не пытаться сначала научить Удава пониманию слов. Заморозить определения v0; затем реализовать минимальную ветку `LLM candidates → formal contrast → LLM adjudication` из уже существующих средств. Только после доказанной пользы рассматривать `ContextualObserver` как новую оптимизацию поиска, новые формальные языки и полноценную интеграцию актуального `udav_core`.

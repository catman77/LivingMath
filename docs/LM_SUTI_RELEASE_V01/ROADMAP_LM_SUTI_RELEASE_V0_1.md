# LivingMath × SUTI — дорожная карта до Release v0.1

**Версия плана:** 2026-11-04  
**Статус:** Proposed release track; не производственный релиз.  
**База:** ASSURANCE-001/002/003 и поставка `LM_SUTI_ASSURANCE_003_DELIVERY.zip`.

## 0. Управленческое решение

Остановить исследования повышения качества Qwen3-0.6B и факторные соревнования моделей. Не заменять их аналогичной серией на 3B/4B. Сохранить данные и негативные результаты, но исключить локальный малый LLM из release-critical path. Оставить один реально работающий hosted generator, возможность ручного предложения кандидата и независимое проверяющее ядро. Наличие иных генераторов — расширяемость интерфейса, не требование к первому релизу.

**Смысл продукта:** воспроизводимое исследование с модельно-независимым правилом допуска знания. Не обещать одинаковое покрытие/качество решений разных моделей. Вердикт принимается независимым checker, не генератором.

## 1. Фактическая исходная точка

- ASSURANCE-003: модель GPT дала 5/5 certifiable classes во всех четырех FF/FC/DF/DC режимах. Qwen3-0.6B дал 0/5 во всех четырех; constrained decoding поднял JSON-valid с 0/7 до 7/7, не содержательную полезность.
- Оригинальный verifier и binder оставлены неизменными между экспериментами; конечные negative gates, direct/compiled replay и metadata-invariance прошли в поставке. Исторический ложный `ENTAILED` (23/24, не 24/24) отклоняется с двумя допустимыми контрмоделями.
- Реализованы изолированные QA-объекты SourceSnapshot, CandidateRecord, Witness, AssuranceDecision, ResearchArtifact; CLI: ingest/propose/check/replay/audit/export; append-only журналы, sha-адреса, автономная проверка без LLM.
- Существующий CLI экспериментальный, `propose` привязан к именам GPT/QWEN. Установленный LivingMath MCP доступен в исследовательских условиях через разрешенный owner loopback, но публичная HTTPS-доступность не подтверждена. Нативный SUTI не исполнялся; Lean binaries обнаружены, formal admission adapter отсутствует. Публичное размещение, управление несколькими пользователями, полноценная эксплуатация не доказаны.
- Проверка source bytes / `rights.origin` НЕ доказывает истинность утверждений источника, авторство или лицензионное право. SHA-256 и hash-chain удостоверяют внутреннюю целостность данных, а не независимую личность автора или юридическую подпись.

## 2. Пользователь и релизный контракт

**Первый пользователь:** технически подготовленный исследователь, который уже пользуется LLM и хочет получать воспроизводимые, ограниченно проверяемые артефакты и легко делиться ими. **Первый формат:** single-user / owner-operated developer preview, устанавливаемый локально в отдельном пространстве и доступный по CLI; MCP-адаптер при наличии возможностей — отдельный управляемый вход, не самостоятельное доказательство готовности.

Один законченный сценарий:

1. Пользователь создает исследование, импортирует 1–3 источника и указывает `rights.origin` и допустимые способы использования.
2. Формулирует утверждение в одной из **поддерживаемых** семантик: `FINITE_PROPOSITION`, `SOURCE_CLAIM`, `EXECUTABLE_BOUNDED`. Свободный текст может породить только *draft*, который требует утверждения человеком, прежде чем попадет в проверяемый контракт.
3. Указанная пользователем модель либо человек предлагает Candidate/ProposalDelta. Система детерминированно привязывает доверенный source/scope, не заменяя содержание гипотезы и не исправляя ошибочные ответы.
4. Независимый verifier выдает `CHECKED_FINITE`, `SOURCE_ATTESTED`, `CONDITIONAL_HYPOTHESIS`, `UNKNOWN`, `HOLD` или `REJECTED` строго в пределах соответствующего предиката. Не показывать «доказано» без доказательства; `PROVED_FORMAL` недоступен.
5. Пользователь видит доступные свидетельства, контрмодели, точный scope и доверенные исходные байты; экспортирует неизменяемый bundle.
6. Второй человек распаковывает bundle и запускает `replay --offline`, не имея исходной модели или подписки; получает тот же логический вердикт или явный отказ из-за отсутствующей зависимости/версии.

**Релизное обещание:** «проверяемый результат с воспроизводимым ограниченным статусом» — не «автоматически правильное научное знание».

**Не входит в v0.1:** локальные 0.6B/3B/4B, автоматическое открытие физических законов, общий эмпирический truth checker, native SUTI, полная SUTI/Syntaxium, продуктивная интеграция Lean и статус PROVED_FORMAL, многопользовательский облачный Research Commons, платежи, глобальный граф знаний, автономное право исполнения, сертификация безопасности, обещания нулевой вероятности ошибок.

## 3. Release gates — работа по этапам, без новой «лестницы»

Этапы выполняются последовательно. Каждый завершается **наблюдаемым артефактом**. Если gate не пройден, править только связанную с ним проблему. Запрещен новый исследовательский модуль ради переименования того же дефекта.

### R0 — Зафиксировать ядро и границы релиза

**Сделать:** выделить точный «source of truth» из `basis002/basis001/code/` + binder002, SHA-биндинги, несовместимости и зависимости. Сформировать `BASELINE_LOCK.json`: source hashes, checker digest, поддерживаемые claim kinds, статус недоступных расширений, перечень tests и контрольного корпуса. Избавиться от дублированных vendor-копий **в упаковке продукта**, не переписывая исторические архивы. Отделить legacy online experiment runners от production runtime. Формализовать политику версионирования и статусы.

**Gate R0:** прежние negative controls, два finite evaluators и offline replay дают прежние logical digests; исторические ZIP остаются неизменными; golden examples воспроизводятся после clean install.

### R1 — Минимально полезный пользовательский контур (MVP)

**Сделать:** один CLI/локальный API сценарий `project new → source add → task draft/review → proposal submit → check → report → export → replay`. Сохранить proposal от человека как равноправный генератор; hosted LLM — заменяемый proposer adapter. UI не нужен; достаточно аккуратного человекочитаемого Markdown/JSON отчета. Не создавать новую математическую DSL или новый verifier. Обработать недопустимые задачи: `HOLD / UNSUPPORTED`, а не выдуманный результат.

**Gate R1:** 3 сценария (конечные модели, source/projection, bounded program) воспроизводятся из чистого каталога; пользователь видит точные scope/assumptions/source refs; экспортированный bundle проходит `--offline` без LLM/сетевых/авторизационных зависимостей.

### R2 — Assurance hardening, безопасное использование

**Сделать:** idempotent request keys; append-only event ledger и atomic write/recovery; миграция версий только с явным новым status и без молчаливой правки claim. Строгая типизация входов, source byte span, content ↔ machine term, rights, provenance, защита от malformed JSON/duplicate keys/path traversal/oversize/подмены полей. Выделить trusted computing base (dispatcher, runtime, schema libs), фиксировать checker digest; публично документировать, что даже «двойной» interpreter не доказывает корректность общего диспетчера. Протестировать offline mode с заблокированными network и model subprocess, не хранить секреты в пакетах.

**Gate R2:** ни один негативный fixture не повышен; все positives получают правильный scoped status; replay и witness hashes совпадают на двух поддерживаемых Python runtimes; crash/resume не дублируют результат; экспорт не содержит ключей/PII по тестам; острые исходные исторические ошибки по-прежнему отвергаются.

### R3 — Реальные пилоты с людьми, а не новые synthetic leaderboards

**Сделать:** 3 пилотных исследовательских кейса, каждый с собственным вопросом, ограничением и владельцем: (a) source/projection SUTI-схемы, (b) конечный контрпример к ложному универсальному утверждению, (c) bounded program invariant. Если кейс из RH/FTL, использовать его только как **реестр утверждений и открытых обязательств**, не как попытку формально доказать RH или физический эффект. Попросить 2–3 внешних технических участников независимо распаковать и воспроизвести bundle. Задокументировать реальную цену ручных действий, частоту HOLD и непонятные статусы.

**Gate R3:** каждый кейс имеет accepted/rejected/unknown artifact и корректно читаемый reason; независимый участник без исходной модели делает успешный offline replay; нулевое количество *обнаруженных* ложных повышений; все блокеры P0/P1 закрыты. Если участники не могут завершить сценарий, релиз откладывается — новая LLM не является решением.

### R4 — Ограниченный Release v0.1 (developer preview)

**Сделать:** установка из чистого окружения и единая команда проверки, README Quickstart, примеры, версия CLI и schemas, manifest/checker hash, changelog, threat model, backup/restore, документация для source-rights и публикации, процедура обновления/отката. MCP endpoint подключать только при полном прохождении auth/TLS/permission tests на реальном внешнем клиенте; иначе оставить CLI как первичный работающий продукт и обозначить MCP отдельно experimental/local-only.

**Gate R4 / GO:** новый технический пользователь без приватного контекста из документации создает/проверяет/экспортирует/воспроизводит артефакт; все R0–R3 сохранены; open blockers P0=0, P1=0; release description не превышает подтвержденных capabilities. Формально назвать `v0.1.0-developer-preview`, не general availability и не сертифицированной scientific-verification platform.

## 4. Критерии релиза

**Непереговорные (hard):**

- false status promotion = 0 на заранее сохраненном наборе негативных регрессий; исторический 23/24 `ENTAILED` дает `REJECTED/UNKNOWN + countermodels`;
- каждый присвоенный `CHECKED_FINITE` имеет конечный воспроизводимый свидетель применительно к версии и scope; `SOURCE_ATTESTED` не печатается как эмпирическая истина;
- отсутствие silent repair машинных терминов, scope, source refs и прав;
- cold-start + offline replay без модели и секретов;
- целостность, version mismatch и export scope обрабатываются явными ошибками;
- reproducibility всех release fixtures = 100% по логическим digests в заявленном окружении;
- security/permissions: ни одна задача не получает execution grant через цитату/статус модели; source-bytes не публикуются вопреки can_embed/publication policy.

**Продуктовые (измеряемые, не математические гарантии):**

- ≥3 end-to-end пилотных задачи разных поддерживаемых видов;
- ≥2 внешних тестировщика смогли выполнить offline replay по README без исходной LLM;
- фиксируется процент успешных проверяемых артефактов, количество HOLD/REJECTED, время человеческого вмешательства и стоимость одного accepted artifact; критерий не оптимизируется под лидерборд;
- usability: сформулировано, как вручную исправить *неправильный* кандидат новым независимым артефактом, не изменяя старый.

**Отдельно за пределами обещания:** нельзя доказать нулевую вероятность ошибки у всех будущих утверждений конечным числом тестов; внешняя физическая/научная истина, правовая экспертиза, фундаментальная полнота проверяющего механизма не входят в гарантии.

## 5. Риски и контрмеры

| Риск | Действие |
|---|---|
| QA «зелёный», но продуктом невозможно пользоваться | R1 + R3 обязательный human workflow и clean install |
| Source attestation трактуется как proof | Разные статусы и UI warning, негативные тесты |
| SHA выдаётся за подлинность автора | Заявлять только integrity / provenance внутри bundle; публикация требует отдельного доверенного механизма |
| Новый генератор меняет тип принимаемых утверждений | Верификатор и admission фиксированы, все кандидаты проходят тот же gate |
| Переписывание негативных результатов | Append-only записи, versioned superseding, read-only history |
| Облако/MCP недоступны | Ручной import кандидата и полностью offline replay сохраняют основной функционал |
| Infinite feature creep | R0–R4, no-native-SUTI/no-Lean/no-Research-Commons-deployment в v0.1 |

## 6. Первое действие

Начать **R0**, затем **R1**. ТЗ и промпт на R0/R1 в том же пакете. Пока **не** запускать новые Qwen-бенчмарки, не менять живой MCP/production, не объявлять release-ready по одним unit-тестам.

## 7. Продолжение после v0.1, не как блокер релиза

v0.2 — поддержка реального формального proof-kernel adapter (Lean) после аудита и более широкий набор типов задач; SUTI native — только с настоящим исполняемым интерфейсом и тестами потерь; v0.3 — согласованный Research Commons MCP publication workflow с permissions, signatures/attestations, multiuser. Порядок может изменяться на основании реального использования, не архитектурных фантазий.

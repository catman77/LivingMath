# White Star: исправление регистрации проекта

Дата проверки: 5 ноября 2026. Установлено в production: **v0.3.0-developer-preview**, deployment `whitestar-onboarding-20261105T041833Z`.

Адрес сохранён: `https://fares-september-rebel-board.trycloudflare.com/mcp`. Перезапущен только HTTP-процесс; процесс туннеля прежний.

## Причина отказа

В `whitestar_dialog_test` отсутствовал `journal.jsonl`: каталог сам по себе не означает регистрацию проекта. White Star использует private assurance workspace. Его создаёт существующий `assurance_project_new`; регистрация legacy research-проекта не заменяет этот вызов.

`Workspace.transact()` корректно выдавал `PROJECT_NOT_FOUND` до сохранения run и запуска численного worker. Но адаптер White Star заменял код на общий `NOT_FOUND`, теряя причину. Описание инструмента не называло обязательный первый шаг. Такой же отказ воспроизведён реальным HTTPS/OAuth MCP-клиентом до исправления.

## Исправление

- Ошибка сохраняет `PROJECT_NOT_FOUND`, указывает `/project`, возвращает конкретный вызов регистрации и порядок повторения запроса.
- `tools/list` для `white_star_explore` и `white_star_status.data.workflow` публикуют обязательную регистрацию.
- Автоматического создания произвольных проектов нет. Неизвестный run_id по-прежнему возвращает отдельный `NOT_FOUND`.
- Input/output schemas и annotations всех 72 инструментов сохранены. Все 75 исходных файлов Белой звезды и численный binary прежние; в рабочем слое изменён только `white_star/mcp.py`.

Проект `whitestar_dialog_test` явно зарегистрирован через MCP с `request_key="project-init-v1"`. Исходное трёхстишие пользователя в сообщении отсутствовало, поэтому в этот проект не добавлялись тестовые тексты или вымышленные результаты. Можно повторить исходный `white_star_explore` с прежними project/request_key/request. Переподключение приложения для этого не требуется; обновление списка инструментов нужно только для отображения нового описания.

## Реальный положительный запуск

Отдельный QA-проект: `qa-ws-onboarding-20261105`. Исходный оригинальный тестовый текст:

> Лампа погасла.  
> Дверь осталась открытой.  
> За порогом рассвело.

SHA256 UTF-8: `012d6c19087c7051e574e3610a6a58d169e2a5af5f62d3d788cb3dcea0a5def7`.

Три понятия, две явно назначенные оси, `cj_v1`, seed42, steps64, candidates_per_step3, frame_size3, decode_first_frames6, semantic_reranking=false. Разметка создана вручную для QA и не выдается за обнаруженную универсальную семантику.

`run_id`: `a3b4180e0c546e340a23074ac20330470aec186e1ff99e3b34ef1d001ffa8a49`.

Через действующий endpoint выполнено: отказ до регистрации → явная регистрация → повтор того же ключа и payload → **COMPLETED** → получение frames/decoder → сохранение и чтение шести LLM-прочтений. Повтор explore возвращает тот же результат; в журнале ровно один `white.start`.

Численный результат: **192 проекции, 21 кадр, 14 качественных режимов**, 6 доступных слотов декодирования. LLM-клиент `gpt-6.1-sol` получил настоящий decoder packet, без tools/web и без серверного LLM-вызова. Первое прочтение:

> Возможное прочтение — передача освещения от внутреннего источника внешнему, причём дверь связывает эти области.

Это сохранённая интерпретация клиента, а не доказательство смысловой новизны или следования из текста. У всех прочтений `INTERPRETATION`, `execution_permission=false`. Native SUTI остаётся `NOT_EXECUTED`; R3 внешних повторов — `PENDING`.

Для просмотра через ChatGPT:

```json
{"name":"white_star_inspect","arguments":{"project":"qa-ws-onboarding-20261105","run_id":"a3b4180e0c546e340a23074ac20330470aec186e1ff99e3b34ef1d001ffa8a49","view":"frames"}}
```

Замените `view` на `decoder` или `readings`, чтобы получить соответствующие сохранённые данные.

## 0. Цель и принцип разделения ответственности

Исправить **две выявленные проблемы**, не изменяя выбранную архитектуру:

1. **P0: направленное голодание перебора** — поиск доказуемо несуществующего контрпримера в направлении A→B забирает все 512 конечных моделей, и на B→A не остаётся бюджета; результат чувствителен к перестановке пары и порядка пар в пакете.
2. **P0: семантическая неадекватность исходной LLM-гипотезы** — в T4 LLM подменяла содержание сообщения (`Said` + `Message...Wrong`) утверждением о фактической ошибке (`WrongEngineer`/`WrongAnalyst`). Сервер корректно проверил переданную формулу, но не мог выявить, что текст **не влечёт** фактичности сообщения. Результат нельзя объявлять доказательством понимания языка.

**Контракт:** LLM формирует онтологию, начальные формулы, текстовые привязки, контрфактические сценарии и пересматривает их по свидетельствам; MCP даёт точные отношения между AST, конечные модели, доказательные сертификаты и сохраняет OPEN semantic obligations. MCP **не** определяет истинный русский смысл, не угадывает референт местоимения, не утверждает истинность содержания сообщения и не запускает LLM внутри движка.

## 1. RCA, привязка к коду

### 1.1. Голодающий цикл

В deployed `contextual/relations.py` функция `pair(...)` итерирует направления в порядке `A_IMPLIES_B`, затем `B_IMPLIES_A`. Для каждого неизвестного направления вызывает `fol.countermodels(candidates, bounds)` с практически всем остатком `work.bounds['max_models']`. `fol.countermodels` стартует с начала каждого раза, без инкрементального cursor. В `engine.py/analyze` пары также обрабатываются последовательно. По завершении `work.models>=512` остальные направления/пары получают `UNKNOWN_BOUND` или остаются недообследованными.

В EXP02:

- `∃e∃a(Said(e,a) ∧ MessageEngineerWrong(e,a))` (`HmsgE`)
- `∃e∃a Said(e,a)` (`Hskeleton`)
- `∃e∃a(Said(e,a) ∧ MessageEngineerWrong(e,a) ∧ MessageAnalystWrong(e,a))` (`HmsgBoth`).

`HmsgE ⇒ Hskeleton` является тавтологическим следованием в каждой модели. Старый `prove_entailment` поддерживает только одинаковые **чисто универсальные** префиксы и не может это доказать, поэтому тратит квоту на невозможный контрпример. Противоположное направление опровергается простой моделью `Said=true, MessageEngineerWrong=false`. При обратном порядке пары контрпример найден за **2** проверки; в исходном порядке тратится весь лимит **512**. Запуски и отчёты в `reference/`.

### 1.2. Семантическая проблема

`contextual/engine.py` проверяет typecheck и сохраняет `source_alignment_status=PROPOSED`; `contextual/relations.py` устанавливает **только отношения между предоставленными формулами**. `OPEN` obligations не представляют собой автоматически лицензированную семантику. Формулы с `WrongEngineer(e)` хорошо типизированы, но исходное «Инженер сообщил аналитику, что он ошибся» не устанавливает, что кто-либо ошибся. Попытка механически вывести фактивность из позиции слов — ошибочна. Исправить **процедуру внешней LLM и API-контракт представления эпистемических обязательств**, а не прививать серверу словарь речевых актов с ложным ореолом доказательства.

## 2. P0: точный слой доказательств без перебора

### 2.1. Расширение безопасного класса доказательств

В `contextual/relations.py` расширить доказательную проверку двух FOL AST:

- Корректная **α-эквивалентность** остаётся P0 первым шагом, с точным сертификатом и независимым checker.
- Для **одинаковых (после α-согласования) префиксов кванторов** `Q1 x1:S1 ... Qn xn:Sn`, где каждый `Qi` может быть `forall` **или** `exists`, а в матрицах нет внутренних кванторов, проверять пропозициональную тавтологичность `matrix(A) ⇒ matrix(B)` по общему набору типизированных позиционных атомов. Отсюда глобально следует `A ⇒ B`: обе операции `forall`/`exists` **монотонны по истинностному отношению** при одинаковом префиксе. Не менять порядок разнородных кванторов.
- Ограничить набор атомов прежним `max_atoms<=10` (≤1024 булевых строк), проверять независимым checker, включать `proof_rule`, `checker_version`, SHA исходных AST/сигнатуры/матриц, точные `prefix_quantifiers_and_sorts`, `atoms`, количество строк, SHA таблицы; булеву оценку не выдавать за FOL-контрмодель. Равенство трактовать как независимый пропозициональный атом **только в направлении достаточной тавтологии**, без неявных аксиом о равенстве.
- Нормализация отрицаний: **узкий sound rule** `¬∀x φ ≡ ∃x ¬φ`, `¬∃x φ ≡ ∀x ¬φ`, устранение двойного отрицания и De Morgan для `and/or`. Рекурсивный ввод в NNF с фиксированным bounded depth/node limit, отслеживание связываний и сортов. Свидетельство `PROVED_NEGATION_NORMAL_FORM_EQ` или иной однозначный proof status с независимой проверкой. Не объявлять свой алгоритм полной процедурой разрешения FOL.
- Если доказаны оба направления логического следования, итог **`PROVED_LOGICAL_EQ`**; это эквивалентность **формул**, без слияния hypotheses и без вывода о корректности трактовки источника. Оставить исходный `PROVED_ALPHA_EQ` для α-случая.

Критически: ННФ в присутствии альфа-переименований проверяется на канонических связях, не на `str.replace`. `∃x(A∧B) ⇒ ∃x A` и `∃x(A∧B∧C) ⇒ ∃x(A∧B)` обязаны доказываться без model enumeration. При несовпадающих кванторных префиксах и других AST вернуть `UNKNOWN_UNSUPPORTED_PROOF_CLASS` — не выдавать ошибочное следование.

### 2.2. Не допускать несовпадения сертификатов с реальностью

В `contextual/checker.py` должен работать **независимый** проверяющий: повторный разбор исходных AST, канонизация, таблица истинности, точный SHA и проверка каждой строки. Никакого `check=lambda cert: cert.status=='PASS'`. Использовать сравнение с учётом типа (не путать `False` и 0 для binder index); защитить от capture, shadowing, разных sorts, перестановок pred arguments, `eq` и вложенных negations. Критические forged certificates отклонять.

## 3. P0: справедливый, детерминированный поиск контрпримеров

### 3.1. Требуемый семантический контракт

Для каждого **не доказанного** направления пары одновременно проверять потенциальные контрпримеры:

- `A=true, B=false` при **всех явно объявленных предпосылках обеих гипотез**;
- `A=false, B=true` при тех же предпосылках.

Один проверенный конечный мир должен оцениваться для обеих формул и обоих направлений, а не запускать один полный перебор до 512 и затем новый с нуля. Одинаковые исходные модели должны давать одинаковые результаты независимо от порядка `pairs` и перестановки `[A,B]` (соответствующим образом инвертировать labels). Сохранять оба опровергающих мира, если существуют. Порядок обхода задавать явно и детерминированно, включая порядок сортов, предикатов и relation tuples.

### 3.2. Планирование бюджета

- После точных доказательств создать **общее множество незавершённых направленных задач** из всех пар. Не запускать полный исчерпывающий поиск первой пары до выделения квоты остальным.
- Предпочтительный способ: `FiniteModelCursor` для каждой пары, который однократно перечисляет модели размеров 1 и 2 (в scope исторического FOL), и на каждой модели оценивает сразу `(A,B,assumptions)`. Активные пары обслуживать в детерминированном round-robin по одной модели/небольшому кванту; допустима эквивалентная схема, если тесты доказывают свойства справедливости.
- Общие ресурсы: `max_models<=512` (считать **реально оценённые уникальные модели** на задачу), `max_steps`, `max_cpu_ms`, прежние CPU/wall/RSS/quota workers. Расход по каждому направлению и паре отражать явно: `models_checked`, `status`, `halt_reason`, `proof_kind`, `counterexample_ref`. Не имитировать «100500 проверок» для вида.
- Существующий `formal_bridge.fol.evaluate` использовать как эталонную семантику closed finite models; вернувшуюся модель перепроверять как объект данных, минимум один независимый verifier (не тот же production code path). `open` модели — UNKNOWN, не контрпримеры.
- Учитывать общие предпосылки строго. Если предпосылки ложны либо UNKNOWN — мир не является контрпримером в области `ALL_CANDIDATE_ASSUMPTIONS_HOLD`; не выдавать из-за этого `FORMULA_FALSE`. Не удалять hypotheses и obligations, не отождествлять разные источники даже при совпадающих AST.
- При превышении допустимых relation cells или лимита объявлять `UNKNOWN_BOUND` **только для реально незакрытых направлений**, сохранять уже доказанные сертификаты и найденные контрмодели. `NO_COUNTERMODEL_WITHIN_BOUND` / `FINITE_SAME_ON_BOUND` не являются теоремой. Если полный конечный класс размера 1–2 перебран, указывать `FINITE_EXHAUSTED`, но не универсальную эквивалентность.
- **Метамодель:** общий статус run `CHECKED_WITH_OPEN_DIRECTIONS` (или эквивалентный ясно определённый status) когда внутренние направления открыты из-за `UNKNOWN_BOUND`, даже если остальные рёбра завершены. `CHECKED` только означает, что вычисление отработало, *не* что все отношения доказаны; метрики `requested/completed/undecided` обязательны.

### 3.3. Главное различающее испытание

При `max_models=32`, только пара `(HmsgE, Hskeleton)` должна иметь **точный proof** `HmsgE⇒Hskeleton` (model_enumerations для этого направления=0) и найденный контрпример обратного `Hskeleton⊭HmsgE`. Обратный порядок возвращает то же логическое отношение и должен стоить сопоставимо. Добавить `HmsgBoth` и третий «тяжёлый» pair под общий лимит 32 или 64 и проверить, что независимый pair с дешёвым контрпримером **не голодает**, хотя другой pair может остаться `UNKNOWN_BOUND`. Два proof-dir + два failed-dir должны агрегироваться без потерь.

## 4. P0: содержательная корректировка на границе LLM ↔ MCP

### 4.1. Обязательный LLM-протокол (без встроенного NLP)

Разработать отдельные документы `LLM_SEMANTIC_AUDIT_PROTOCOL_RU.md` и `LLM_REPAIR_PROMPT_RU.md` для клиента/кодового агента, которые применяются **до** `semantic_bridge_register` и **после** `semantic_bridge_analyze`.

LLM на стадии черновика обязана разделять, если это релевантно данному тексту:

1. **Утверждение о факте vs сообщение/убеждение/желание/гипотеза о факте** (factivity leak).
2. Области действия кванторов и отрицаний.
3. Референт анафоры и явно неразрешённые альтернативы.
4. Пресуппозицию существования и отдельную формальную предпосылку.
5. Время/модальность и недостаточность текущего FOL.

Для каждого обнаруженного риска — указать буквальный фрагмент источника, альтернативные кандидатные AST или `unsupported`, явный `obligation(status=OPEN)` и сформулированный **различающий сценарий**. Если риск не удалось содержательно закрыть, оставить `OPEN`, не выдумывать семантическую санкцию.

**T4:** первоначальную форму `Said(e,a)∧WrongEngineer(e)` пометить `RISK_FACTIVITY_LEAK`; допустимая отдельная модель сообщения `Said(e,a)∧MessageEngineerWrong(e,a)` всё равно остаётся `PROPOSED`. Разобрать альтернативу про аналитика; **не** утверждать истинность `WrongEngineer(e)` из source без другого основания. Само имя `MessageEngineerWrong` — лишь LLM-назначенная сигнатура, не гарантия верности.

**T6:** «После проверки...» требует порядка событий. `∃h Checked(h)∧Accepted(h)` не выражает «после», поэтому должно оставаться помеченным как `LOSSY_FORMALIZATION` с `TEMPORALITY:OPEN`; если нет поддерживаемого языка — корректное `LANGUAGE_INSUFFICIENT`/`ABSTAIN`. Нельзя исправлять молчаливым ослаблением.

### 4.2. Минимальная опциональная механическая поддержка (если действительно нужна)

Текущий интерфейс уже принимает `obligations[{id,kind,description,status=OPEN,source_links,...}]` и `construction_trace`. **Не добавлять новый tool**, если хватит существующего контракта. Можно добавить опциональное поле `semantic_risk_ledger` **только в новом opt-in контракте** (и лишь если проведён RCA, что существующих полей недостаточно), которое механически валидирует точные ссылки на source/AST, но **никогда** автоматически не присваивает `SOURCE_ENTAILS`, `NONFACTIVE_VERIFIED` или `SEMANTICALLY_CORRECT`.

Не кодировать маркеры «сообщил», «думал», «считает» как словарь server-side семантического разрешения. Не добавлять эмпирическую «оценку правдоподобности» формул по численному CAD и не заменять semantic review автоматической эвристикой.

### 4.3. Как измерять, исправлено ли что-то в семантике

Нужен отдельный слепой контроль из `reference/NEXT_AB_PROTOCOL_RU.md`: замороженный baseline draft, одинаковый токенный budget и revision turns для no-MCP / базового FOL / Semantic Bridge; независимая human adjudication. Для текущего PATCH002 приёмочным условием является **наличие строго описанного протокола и корректного удержания OPEN**, а не выдуманный % uplift.
